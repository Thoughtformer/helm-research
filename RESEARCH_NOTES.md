# Helm — questions, observations, and next tests

**Public summary prepared October 18, 2026.** These are selected summaries of the private project's working records. They are not new experiments, an independently audited result, or a substitute for raw evidence. No private inputs, answer keys, credentials, or internal infrastructure details are included.

## Case 1: execution is not competence

**Question:** If a task can pass through a control plane, what have we actually demonstrated?

**Recorded observation:** The project separated a functioning runtime and reconstructable evidence path from the worker's ability to answer correctly. Some bounded qualification work did not establish worker competence. Readiness was left unknown rather than promoted from runtime success.

**Lesson:** The transport, authority boundary, structural contract, semantic result, and human usefulness need separate assessment.

**Still open:** What task and worker combination can earn fresh, held-out evidence without weakening verification?

## Case 2: an incomplete plan is not an executable plan

**Question:** How should a system respond when inference returns text but not a usable result?

**Recorded observation:** An authorized planning request terminated at its output limit without a usable plan. The record preserves the failed attempt and distinguishes subsequent local validation repairs and synthetic tests from successful live planning. No executable plan resulted from that failed request.

**Lesson:** Connection discovery, authentication, completed inference, valid structured output, and an authorized executable action are distinct states.

**Still open:** Can a separately authorized, bounded request produce a usable proposal that survives validation and exact-action review? This public page reports no successful follow-up experiment.

## Case 3: a benchmark advantage can have another explanation

**Question:** Did orchestration help, or did it provide a different set of tools?

**Recorded observation:** Early bounded BUILD/OPERATE comparisons showed advantages under fixture-specific conditions that included unequal tool access. Planning did not have verified live success.

**Lesson:** Those observations do not isolate the effect of orchestration. Claims must stay narrower than the experiment.

**Still open:** How would a direct baseline compare when both lanes have equivalent resources, task inputs, verification, and opportunities for human help? Any new evaluation needs its own authorization and design; it is not represented here as completed.

## Case 4: usability belongs in the evidence

**Question:** Can the owner operate a workflow and correctly interpret its receipt?

**Recorded observation:** The project developed a local interface and provider integration but also recorded incomplete planning, installation restrictions, and wider test failures. Passing focused tests did not establish the final installed experience.

**Lesson:** A convincing demo and a usable system are different milestones. Human understanding of permissions and uncertainty is part of the question.

**Still open:** Which bounded workflow produces a genuine, understandable first win for the owner?

## A bounded learning plan

For future authorized work, I want to improve at:
- defining the question, scope, baseline, success criteria, and stop conditions before execution;
- preserving unsuccessful and incomplete outcomes;
- keeping development cases separate from fresh qualification;
- accounting for human work and total resource use;
- using deterministic verification where it can test the requirement, while acknowledging its limits;
- distinguishing owner testing from independent usability research.

These are learning goals. This document does not authorize new experiments or claim that these methods have all been demonstrated.

## What “governance” means here

The immediate subject is practical governance of a small software system: who can approve an action, which resources it can use, how boundaries are checked, and what evidence explains a result. It is a way to learn about safety and governance through implementation. It does not establish institutional policy expertise or a solution to frontier AI risks.
